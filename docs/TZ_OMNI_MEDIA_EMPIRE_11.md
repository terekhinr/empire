## 2. Универсальные функциональные требования (общие для обоих вариантов)

Эти требования сохраняют силу независимо от варианта реализации:

1. **Единая контент-сущность** со статусами `draft → pending_review → approved → rendering → published → failed` и переходами через очередь.
2. **Идемпотентные публикации**: повторный вызов адаптера не создаёт дубль; ключ `(content_id, channel)` уникален.
3. **Единый дашборд модерации**: текст, видео (с превью и опцией пересборки), статистика, мониторинг ресурсов, журнал ошибок, очередь job (с прогрессом).
4. **Очередь job** с приоритетами: `realtime > publish > render > scout` и ограничением параллелизма по типу.
5. **Логи и метрики**: структурированный JSON-лог по каждому job (`id, type, persona, duration_ms, cpu, mem_peak, exit, error`).
6. **Платёжное ядро**: чек по 54-ФЗ, webhook idempotency, журнал транзакций, отдельная БД от контентной.
7. **RBAC дашборда**: минимум 2 роли — `admin`, `editor`.
8. **Резервное копирование** ежедневно: контентная БД, платёжная БД, конфиги; off-site копия раз в неделю.
9. **Аварийные стопы**: глобальные флаги «остановить публикации», «остановить рендер», «остановить продажи» в дашборде.

## 3. ВАРИАНТ A — «На текущей инфраструктуре»

> Цель — выжать максимум из VPS 4/8/120 и существующего кода (Python/aiogram/Streamlit/FastAPI/SQLite/FAISS), без миграции платформы.

### 3.1. Архитектура

- **systemd** управляет процессами; роли:
  - `empire_main` — бот, шедулер, генерация (как сейчас).
  - `empire_dashboard` — Streamlit.
  - `empire_webapp`, `empire_gdepar` — FastAPI-сайты.
  - **(новый)** `empire_worker` — очередь длительных задач (видео, scout, рендер) на базе **RQ/Arq** (Redis) **или** SQLite-очередь (если решаем не ставить Redis).
  - **(новый)** `empire_sales` — платёжный бот на aiogram + webhook FastAPI (изолированный код и БД `empire_sales.db`).
  - **(новый)** `empire_video` — отдельный systemd-таймер, активный 02:00–06:00, рендерит из очереди `render`.
- **БД:**
  - `empire.db` (SQLite WAL) — контент, разведка, статусы (как сейчас, с расширением схемы под video_jobs).
  - `empire_sales.db` (SQLite WAL) — заказы, чеки, подписки.
  - Раз в сутки `sqlite3 .backup` обеих БД в `/var/backups/empire/`.
- **Файловая система:**
  - `media/raw/<job_id>/` — исходники yt-dlp (TTL 24ч);
  - `media/render/<job_id>/` — финальные ролики (TTL 7 дней после публикации, потом архив/удаление);
  - `media/srt/<job_id>.srt` — субтитры (хранить отдельно от готового рендера);
  - **Алёрт** при свободном месте < 20 ГБ → автоматическая остановка `render`.

### 3.2. Видео-фабрика (Night Shift) — ограничения и спецификация

- Окно работы: **02:00–06:00 МСК** через `systemd OnCalendar`.
- Конкурентность: **1 транскрибация одновременно** (CPU); **до 2 ffmpeg-задач** при низкой нагрузке.
- **Whisper:** `faster-whisper`, модель `small` или `base`, `int8`, beam=1 — баланс качества/CPU.
- **Длительность исходника:** мягкий лимит 30 мин (длиннее — резать сначала по таймкодам).
- Артефакты на каждый job: `raw.mp4`, `transcript.srt`, `cuts.json` (от LLM), `hardsub_<n>.mp4`.
- **Хардсаб только после approve в дашборде.** До этого — softsub в превью.
- **Готовность к публикации:** утром редактор видит в дашборде «готовые к выгрузке», подтверждает; адаптеры YT/VK/Dzen/TG публикуют согласно матрице.

### 3.3. Коммерческое ядро (на той же машине, но изолированно)

- Отдельный процесс `empire_sales`, отдельная БД, отдельный домен/субдомен для webhook.
- **YooKassa**: товары/подписки, чеки, статусы заказов в `empire_sales.db`.
- **Telegram Stars**: микро-донаты «Ленина» / «Где пар» (без 54-ФЗ если строго донат, иначе чек).
- Связь с контентом — только **по `content_id`** (для метки «куплено пользователем X»), без прямых JOIN-ов между БД.
- **Аварийный план:** при падении `empire_main` платёжный бот остаётся доступным.

### 3.4. Очередь и адаптеры публикации

- Универсальный интерфейс адаптера:
  - `prepare(content) -> Asset`
  - `publish(asset, target) -> PublishResult`
- Реализовать минимум: **TG, VK Wall, VK Клипы, YT Shorts, Дзен RSS, VC.ru, MAX**.
- Все вызовы — через `worker` с ретраями и rate-limit-конфигом на канал.

### 3.5. Лимиты ресурсов на хосте (cgroups через systemd)

| Сервис | MemoryMax | CPUQuota |
|--------|-----------|----------|
| `empire_main` | 3.5G | 200% |
| `empire_dashboard` | 1G | 100% |
| `empire_worker` | 2G | 150% |
| `empire_video` (ночью) | 4G | 350% |
| `empire_sales` | 512M | 50% |

Конкурентное окно: ночью `empire_video` имеет приоритет; днём — генерация и публикация.

### 3.6. Фазы реализации (вариант A)

| Фаза | Содержание | Критерий приёмки |
|------|------------|------------------|
| A.1 | Стабилизация ядра, WAL, единый дашборд, расширение схемы БД, бэкапы | дашборд сохраняет/публикует без `database is locked` под нагрузкой; ежедневный бэкап |
| A.2 | Адаптеры публикации (VK, VC.ru, MAX, Дзен) | публикация хотя бы 1 поста на каждый канал из дашборда |
| A.3 | Разведка (Telethon Spy + YT API) | разведданные приходят в дашборд, можно «создать черновик» |
| A.4 | Видео-фабрика (Night Shift) | первое видео полного цикла (yt-dlp → cuts → hardsub → publish) автоматически за ночь |
| A.5 | Коммерческое ядро (отд. сервис) | приём оплаты через YooKassa, чек, выдача продукта |
| A.6 | Партизаны (нейрокомментинг, парсер карт) | dry-run + ручной режим, потом контролируемый авто |

### 3.7. Когда понадобится upgrade железа

- Стабильно >70% CPU в окне 02:00–06:00 — добавить vCPU.
- Стабильно >70% RAM в пике — добавить RAM.
- БД `empire.db` >1 ГБ или >50 r/w/s — мигрировать на PostgreSQL.
- Объём `media/` устойчиво растёт после политики TTL — выделить S3/Object Storage.

## 4. ВАРИАНТ B — «Чистый лист» (без привязки к существующей инфраструктуре)

> Цель — спроектировать оптимально под задачи v11 (видео, монетизация, разведка), не оглядываясь на текущий VPS и Python-код.

### 4.1. Инфраструктура (рекомендация)

| Компонент | Рекомендация | Обоснование |
|-----------|---------------|-------------|
| Compute «горячий слой» | **2× VPS среднего класса** (web/api + bot) с балансировщиком | устранение SPoF, отказоустойчивость публикации и платежей |
| Compute «видео» | **GPU-инстанс по требованию** (RunPod / Vast.ai / Selectel GPU-pool) либо **внешний ASR API** | Whisper на GPU = ×10 быстрее, не блокирует продукт |
| Object storage | **S3-совместимое хранилище** для media/raw/render/srt | устранение упирания в 120 ГБ SSD |
| База контента | **PostgreSQL 16** (managed) | реальная конкурентная запись, миграции, JSONB |
| Кэш/очередь | **Redis** (managed) | очередь job, rate-limit, idempotency keys |
| Поиск/RAG | **Qdrant** (managed) или **pgvector** | проще FAISS в эксплуатации, есть фильтры и метаданные |
| LLM | **OpenRouter** + локальный fallback (например, `Qwen2.5-7B-Instruct` через vLLM на GPU-узле) | контроль расходов и SLA |
| ASR | **Deepgram / AssemblyAI** или **faster-whisper на GPU** | предсказуемое время рендера |
| Платежи | **отдельный сервис «billing»** с YooKassa + Telegram Stars + Stripe (опц.) | изоляция, аудит, PCI-чистота |
| Observability | **Grafana + Loki + Prometheus** (managed Grafana Cloud free tier на старте) | реальный мониторинг очередей, ошибок, расходов |
| Деплой | **Docker Compose** на первом этапе, **Nomad/Kubernetes** при росте | повторяемые окружения, простые откаты |
| CI/CD | **GitHub Actions** или **GitLab CI** | тесты, линт, сборка образов |
| Секреты | **Vault** или **Doppler/1Password Connect** | без `.env` на серверах |

### 4.2. Сервисы (логические границы, язык — на усмотрение исполнителя)

- **content-api** — REST/GraphQL над контентом и публикациями (Python/FastAPI или Go/Fiber).
- **dashboard** — SPA (Next.js/Remix) поверх `content-api`, с RBAC, очередями, превью видео.
- **bot-gateway** — Telegram/MAX/VK ботов как тонкие адаптеры, общая бизнес-логика — в `content-api`.
- **scout** — отдельный сервис разведки (Telethon, YT Data API, RSS), пишет в Postgres + Qdrant.
- **render** — stateless worker с GPU autoscale (cold-start tolerant), задачи через Redis/Sidekiq/RQ.
- **billing** — отдельный сервис, отдельная БД, отдельный домен/SSL.
- **publishing** — адаптеры площадок, изолированный сервис с rate-limit и ретраями.

### 4.3. Преимущества варианта B

- Видео-pipeline быстрее в **~10 раз** (GPU ASR).
- Никаких «database is locked» (Postgres).
- Платежи изолированы от контента (выживаемость продаж при инциденте).
- Прозрачные расходы: можно гасить GPU между ночами.
- Поддержка нескольких разработчиков (CI/CD, образы, миграции).

### 4.4. Стоимость и time-to-market (порядок величин)

- **Cost:** старт ~60–120 $ / мес (2× VPS + managed Postgres/Redis + GPU on-demand), при росте — выше; **больше**, чем нынешние 1000 ₽/мес.
- **Time-to-market:** 6–10 недель полного цикла vs ~3–5 недель доработки варианта A.
- **Перенос данных:** SQLite → Postgres, FAISS → Qdrant, media → S3 — отдельная миграционная фаза.

### 4.5. Фазы реализации (вариант B)

| Фаза | Содержание | Критерий приёмки |
|------|------------|------------------|
| B.1 | Инфраструктура (Postgres, Redis, S3, CI/CD, observability) | окружения dev/prod, deploy за одну команду |
| B.2 | Контент-API + дашборд (минимальный CRUD контента, статусы, RBAC) | редактор работает в новой панели вместо Streamlit |
| B.3 | Адаптеры публикации (TG/VK/MAX/VC.ru/Дзен/YT) | веерная публикация одной кнопкой |
| B.4 | Видео-render на GPU (Deepgram или whisper-GPU + ffmpeg) | первый авто-цикл за минуты, не за часы |
| B.5 | Billing-сервис, продукты, чеки | E2E покупка инфопродукта с чеком |
| B.6 | Scout + нейрокомментинг + парсер карт | разведка и UGC в новом дашборде |

## 5. Сравнение вариантов

| Аспект | Вариант A (текущая инфра) | Вариант B (чистый лист) |
|--------|---------------------------|--------------------------|
| Стартовые затраты | ≤ текущих | в 3–10× выше |
| Скорость запуска | 3–5 недель | 6–10 недель |
| Видео-фабрика | работает ночью, медленно | работает по требованию, быстро |
| Отказоустойчивость | один хост — SPoF | мульти-хост, S3, managed БД |
| «database is locked» | возможен при росте | исключён (Postgres) |
| Подходит для масштабирования продаж | до десятков заказов/день | сотни–тысячи |
| Поддержка командой | сложно при росте | проще, есть CI/CD/мониторинг |
| Когда выбирать | бюджет 1–5 тыс ₽/мес, эксперимент | если монетизация — целевая, нужен SLA |

**Рекомендация:** старт по варианту A до фазы A.3 включительно (адаптеры + разведка). Параллельно — **проектирование варианта B**. Перейти на B после первых выручек, чтобы инфраструктура не упиралась в одну машину.

## 7. Критерии успеха v11

1. Видео-фабрика выпускает **N ≥ 3** утверждённых Shorts/сутки в авто-режиме без вмешательства днём.
2. Платёжное ядро принимает **первую** оплату с корректным чеком (54-ФЗ или донат, в зависимости от продукта).
3. Дашборд показывает: очередь рендера, статус публикаций, выручку, свободное место SSD/объект-хранилища.
4. Аварийный стоп любого подсервиса не валит остальные.
5. Бэкапы восстанавливаются на тестовом окружении за < 30 минут.
