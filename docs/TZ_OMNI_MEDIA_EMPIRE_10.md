# Техническое задание (исходное)

**Проект:** Омни-Медиаимперия 10.0 (Data-Driven, UGC & Spy)  
**Версия ТЗ:** 1.0  
**Статус:** утверждение к реализации  
**Целевая инфраструктура:** выделенный VPS **4 vCPU, 8 GB RAM, 120 GB SSD**, ОС Linux, reverse-proxy Nginx (уже в эксплуатации).

---

## 1. Цели и границы проекта

### 1.1. Бизнес-цели

- Построить **автоматизированную фабрику контента** с веерной публикацией по матрице каналов и персон.
- Обеспечить **data-driven** управление: разведка конкурентов, тренд-аналитика (в т.ч. YouTube Shorts), партизанский маркетинг — с выводом в **единый дашборд**.
- Захватывать **бесплатный UGC-трафик** при сохранении единого визуального и текстового стиля персон.
- Минимизировать ручную рутину редактора: модерация, публикация, мониторинг — из одной панели.

### 1.2. Технические цели

- **Лёгкость ежедневной работы:** один вход (дашборд), предсказуемые статусы сущностей, отсутствие «залипаний» БД и дублей процессов.
- **Эффективное использование VPS:** приоритет CPU/RAM для RAG, транскрибации и пакетной обработки; диск — для медиа, индексов и логов с ротацией.
- **Модульность:** независимые подсистемы (оркестратор, разведка, публикация, веб) с явными контрактами данных.

### 1.3. Вне объёма (на усмотрение заказчика, не блокирует MVP)

- Полная замена SQLite на PostgreSQL (допустима как отдельная фаза при росте нагрузки).
- Собственный мобильный клиент.
- Полный CRM/email-маркетинг уровня enterprise.

## 2. Исходные активы и ограничения

### 2.1. Уже развёрнуто (зафиксировать как базу ТЗ)

| Компонент | Назначение |
|-----------|------------|
| VPS 4/8/120 | единая точка исполнения всех сервисов |
| SQLite `empire.db` | черновики, статусы, журналы операций (режим **WAL** обязателен) |
| FAISS + sentence-transformers (CPU) | RAG по персонам |
| Оркестратор (`main.py`) | генерация, шедулер, TG, RAG |
| Дашборд (`dashboard.py`, Streamlit) | модерация, аналитика, мониторинг |
| FastAPI (`web_app.py`, `gdepar_app.py`) + Nginx | публичные сайты |
| API: OpenRouter, YesAI (SD) | LLM и изображения |

### 2.2. Ограничения среды

- Нет выделенного GPU — тяжёлые модели ограничить по размеру и очереди задач.
- Сетевые лимиты внешних API — обязательны rate-limit, retry с джиттером, кэширование.
- Один хост — **запрещено** несколько экземпляров одного Telegram-бота с одним токеном (конфликт long polling).

## 3. Рекомендуемая архитектура (предложение исполнителя)

### 3.1. Общий принцип

**Монолитные сервисы с чёткими границами процессов** под управлением **systemd**: проще сопровождать на одном VPS, чем Kubernetes. Асинхронные и длительные задачи — в **отдельном worker-процессе** (очередь на SQLite или лёгкий Redis по необходимости), чтобы не блокировать polling бота и HTTP сайтов.

### 3.2. Рекомендуемый стек (не жёсткая привязка к языку)

| Слой | Рекомендация | Обоснование |
|------|----------------|-------------|
| Оркестратор, разведка, интеграции | **Python 3.12+**, asyncio | уже есть код, экосистема Telethon/httpx/SQLAlchemy |
| Публичные сайты | **FastAPI** | уже есть, минимальный overhead |
| Дашборд | **Streamlit** (MVP) или **Reflex**/лёгкий **React+API** при росте UI | Streamlit — быстрее всего для «Ока Саурона» |
| БД | **SQLite (WAL)** + периодический бэкап | достаточно до ~средней конкуренции записей; миграции — по мере усложнения схемы |
| Очередь задач | **SQLite-очередь** или **Redis** (если появятся воркеры >1) | разгрузка VPS от лишних сервисов на старте |
| Reverse proxy | **Nginx** | TLS, статика, лимиты |
| Транскрибация Shorts | **faster-whisper** (CPU, int8) или внешний API при нехватке CPU | контроль нагрузки на 4 ядра |
| Логи | **journald** + ротация файловых логов модулей | без тяжёлого ELK на VPS |

### 3.3. Распределение ресурсов VPS (ориентир)

| Назначение | RAM (ориентир) | Примечание |
|------------|----------------|------------|
| Оркестратор + embeddings | 2–3.5 GB | sentence-transformers + FAISS |
| Streamlit + FastAPI | 0.5–1 GB | пики при одновременных пользователях |
| Worker (scout/YT/транскрибация) | 1–2 GB | ограничить concurrency (1–2 тяжёлых job) |
| ОС + кэш + запас | 1–2 GB | мониторинг в дашборде |

При превышении — **очередь и отложенный запуск** задач, не масштабирование «всё сразу».

### 3.4. Модель данных (логическая, расширение `empire.db`)

Единые сущности (таблицы или эквивалент):

- **Контент-единица:** `id`, `persona_key`, `format` (лонг/шорт/коммент), `text`, `media_refs`, `status` (draft / pending_review / approved / published / failed), `created_at`, `published_at`, `targets` (JSON массив каналов).
- **Публикация:** связь контент ↔ канал ↔ внешний `post_id`, ошибка, timestamp.
- **Разведка:** источник (RSS / TG / VK / YT), сырой payload (или путь к файлу), извлечённая тема, score (ER / просмотры), связь с черновиком при генерации.
- **Настройки каналов:** credentials по ссылке на env/secret store, не в коде.

## 5. Функциональные требования по модулям

### 5.1. Омни-Оркестратор (центральный роутер)

**Назначение:** единая точка планирования генерации, статусов и веерной публикации.

**Требования:**

- Smart prompting: сборка системного промпта из роли персоны, сезона, RAG-чанков, файлов стиля (для Бороды — явное чтение `style_author.txt`, `my_strategy.txt`).
- Garbage collector медиа: политика хранения (например, N дней для `media/draft_*`), не трогать опубликованные без флага архивации.
- Конвертация Markdown → HTML для Telegram с валидацией тегов (как сейчас или улучшение).
- **Адаптеры публикации** — единый интерфейс, например `publish(content_id, channel_type) -> PublishResult`:
  - Telegram (уже есть);
  - VK Wall API;
  - MAX (официальный API после верификации ИП);
  - VC.ru API;
  - RSS/XML для Дзена;
  - при необходимости: VK/MAX отложенная очередь.
- Идемпотентность: повторный вызов публикации не создаёт дубликатов (проверка `publications` по `(content_id, channel)`).

### 5.2. Око Саурона (единый дашборд)

**Требования:**

- Модерация лонгридов: список `pending`, редактирование текста, сохранение без блокировок БД (WAL, короткие транзакции, при необходимости отдельное соединение на save).
- Лента ТЗ для Shorts: очередь тем из YT/разведки с полями «заголовок, хук, CTA, длительность, B-roll идеи».
- Сводная статистика: по персонам, статусам, каналам; экспорт CSV опционально.
- Системный мониторинг: RAM, SSD, размер `media/`, размер БД, последние ошибки публикаций.
- Роль доступа: MVP — один админ (пароль/env); дальше — HTTP Basic за Nginx или SSO.

### 5.3. Модуль разведки (`scout` + расширения)

**5.3.1. News Parser (RSS)**

- Источники: РБК, Smart-Lab и др. из конфига.
- Периодичность: cron/systemd timer или job в worker.
- Выход: нормализованные записи в таблицу разведки + дедупликация по URL/хэшу.

**5.3.2. Spy Parser (Telethon)**

- Учётные данные в env, сессии на диске с правами `600`.
- Сбор постов конкурентов, расчёт **ER** (лайки/просмотры/комментарии — по доступным метрикам канала).
- Отбор аномалий по порогам из конфига.
- Экстракция темы (LLM или эвристики) → запись в разведку → опционально «создать черновик» из дашборда или авто-в очередь (флаг).

**5.3.3. YT-Аналитик**

- Источник: YouTube Data API v3 (квоты, ключ в env).
- Выборка трендовых Shorts за окно (например, 30 дней) по нише/ключам из конфига.
- Загрузка аудио/видео — **в worker**, с лимитом параллелизма.
- Транскрибация → сценарий Shorts (LLM) → запись в ленту ТЗ дашборда.

### 5.4. Генератор трафика (UGC и партизаны)

- **RSS для Дзена:** генерация валидного `rss.xml` (обновление по расписанию, URL в Nginx).
- **VC.ru:** публикация лонгридов через API, статусы в БД.
- **Нейрокомментинг (Telethon):** отдельный режим с жёсткими лимитами (частота, задержка, стоп-слова); учётные данные тех.аккаунтов и прокси — только env; лог каждого действия.
- **Парсер Яндекс.Карт:** сбор карточек для `гдепар.рф` (гео, часы, рейтинг); хранение в SQLite или отдельных JSON с индексом в БД.

## 6. Нефункциональные требования

### 6.1. Надёжность

- Все сервисы под **systemd**, `Restart=always`, лимиты `MemoryMax` по желанию.
- Бэкап `empire.db` ежедневно (sqlite `.backup` или копия в off-site при наличии).
- Единственный процесс бота на токен.

### 6.2. Безопасность

- Секреты только в `.env` (права 600) или в systemd `EnvironmentFile`.
- Не логировать токены и PII.
- Для Telethon/нейрокомментинга — отдельные сессии и rate limits.

### 6.3. Наблюдаемость

- Структурированные логи: `module`, `event`, `content_id`, `duration_ms`, `error`.
- Алерты MVP: дашборд + опционально TG-уведомление админу при `N` ошибках публикации подряд.

### 6.4. Производительность

- RAG: ограничение размеров чанков и top-k в промпте.
- Worker: не более **1** одновременной транскрибации длинного ролика на CPU без очереди.

## 7. Фазы внедрения и критерии приёмки

### Фаза 1 — Ядро (текущее состояние + доработки)

**Критерии приёмки:**

- VPS, Nginx, SQLite WAL, оркестратор, дашборд, FastAPI-сайты работают под systemd.
- Нет дубликатов процесса бота; дашборд сохраняет черновики без `database is locked` при нормальной нагрузке.

### Фаза 2 — Омни-оркестратор и адаптеры

**Критерии приёмки:**

- Реализованы адаптеры минимум: **VK**, **RSS Дзен**, **VC.ru** (хотя бы черновик публикации с ручным подтверждением в дашборде при риске).
- Промпт «Бороды» включает содержимое `style_author.txt` и `my_strategy.txt` (версии файлов логируются хэшем).
- Единая таблица/журнал публикаций с отображением в дашборде.

### Фаза 3 — Разведка

**Критерии приёмки:**

- RSS-разведка пишет в БД и отображается в дашборде.
- YT Shorts: не менее **K** тем в неделю в ленту ТЗ (K из конфига, напр. 10) при действующем API-ключе.
- Spy Telethon: отбор **M** постов-аномалий в сутки, карточка в дашборде с ссылкой на источник.

### Фаза 4 — Масштабирование UGC

**Критерии приёмки:**

- Нейрокомментинг: сценарии включения/выключения, отчёт по отправкам.
- Парсер Яндекс.Карт: не менее **P** записей в базу агрегатора (P из конфига).
- Пайплайн Shorts: экспорт сценария в формат для внешней съёмки (PDF/Markdown).

## 8. Риски и меры

| Риск | Мера |
|------|------|
| Бан аккаунтов при агрессивном комментинге | лимиты, ручное одобрение, «dry run» |
| Квоты YouTube / VC | кэш, очередь, fallback на ручной импорт ссылки |
| Перегруз CPU | очередь worker, отключение тяжёлых job в часы пик генерации |
| Рост SQLite | WAL, вакуум по расписанию, план миграции на PostgreSQL при превышении порогов |
