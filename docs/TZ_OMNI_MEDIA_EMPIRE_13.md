## 0. Что нового в v13 по сравнению с v12

1. **Гибридная архитектура VPS + локальный ПК с GPU.**
   - VPS — «витрина» 24/7: сайты, дашборд, боты, базы, очередь задач.
   - Локальный ПК с **RTX 4060 (8 GB VRAM)** — «тяжёлый воркер»: видео-рендер (NVENC), Whisper, RAG-embeddings на CUDA, опционально Stable Diffusion.
2. **WireGuard-туннель** как основной транспорт между VPS и ПК.
3. **Локальная генерация изображений** как опция (Stable Diffusion XL / 1.5) вместо платных API.
4. **NVENC-рендер** в `ffmpeg`.
5. Введены **два архитектурных сценария на стороне заказчика** (Гибрид / Соло-локалка). В этом ТЗ они оцениваются и для каждого даны рекомендации.

## 1. Анализ слабых мест v13 (обязательно зафиксировать)

### 1.1. Аппаратные ограничения локального ПК

| № | Риск | Последствие | Рекомендация |
|---|------|-------------|--------------|
| H1 | **i7-3770 (Ivy Bridge, 2012)** + DDR3, PCIe 3.0 | RTX 4060 теряет до 5–10% на bus-bound задачах, инференс upscaling/SDXL может упираться в CPU/DDR3 | приемлемо для Shorts/Whisper; **не строить** на нём долгосрочную тяжёлую генерацию SDXL-1024 |
| H2 | **VRAM 8 GB** | SDXL базовый + рефайнер не помещается без `--medvram`, Whisper large-v3 (~6–10 GB) на грани | использовать **Whisper medium int8** или **distil-whisper**, **SD 1.5** или **SDXL Turbo** с low-VRAM режимом |
| H3 | **Диски C:/F:/G: заполнены на 95–99%** | невозможно установить CUDA, ffmpeg, модели и кэш рендера | **блокирующая задача**: освободить ≥150 GB на отдельном NVMe (рекомендуется отдельный диск под `D:\models` и `D:\render`) до начала работ |
| H4 | **Win 10 Pro прошёл EOL (14.10.2025)** | без security-обновлений, риски в роли «production-воркера» | один из путей: (1) ESU/обновление до Win 11, (2) **WSL2 Ubuntu 22.04** для рабочей нагрузки + nvidia-toolkit-for-WSL, (3) перейти на dual-boot Linux |
| H5 | **Антивирус Windows / Defender** | блокирует `yt-dlp`, кэш моделей, неподписанные бинарники | исключения по папкам моделей и рендера, согласие пользователя |
| H6 | **Электричество и обновления Windows** дома | падение воркера в любой момент | политика «работаем по расписанию», отдельный UPS, отключённые автообновления в часы рендера |

### 1.2. Сеть и связь VPS ↔ ПК

| № | Риск | Последствие | Рекомендация |
|---|------|-------------|--------------|
| N1 | **Аплоад из дома лимитирован** (типично 50–200 Mbit) | передача 1 ГБ рендера занимает минуты | складывать готовые ассеты в **S3-совместимое хранилище** (Selectel/Yandex Object Storage) и публиковать оттуда; либо отдавать через CDN |
| N2 | **Симметричный WireGuard на стороне ПК** | при NAT/CGNAT нужно подключаться **из ПК к VPS** | туннель инициируется с ПК, на VPS — `wg0`-сервер; «постоянный IP» дома желателен, но не обязателен |
| N3 | **Cloudflare Tunnel ограничения** (вариант пользователя «Б») | гонять тяжёлый видеотрафик через CF Tunnel запрещено ToS | CF Tunnel — только для HTTP/UI; видео и большие файлы — через WG/S3 |
| N4 | **Простой туннеля** | очередь рендера встанет | watchdog WG + автозапуск + алёрт в дашборде «PC offline» |

### 1.3. Программная стабильность

| № | Риск | Последствие | Рекомендация |
|---|------|-------------|--------------|
| P1 | **CUDA/NVENC сборка ffmpeg на Windows** | сложная конфигурация, частые конфликты версий | использовать готовый **ffmpeg-master-latest-win64-gpl-shared** (gyan.dev/BtbN) или ffmpeg внутри WSL2; зафиксировать версии моделей и инструментов в `requirements.txt`/`environment.yml` |
| P2 | **PyTorch + CUDA на Win10** | версионная зависимость, поломки при обновлениях | пин-версии CUDA toolkit и `torch==x.y.z+cuYYY`; всё ставить в **отдельный venv/conda** окружении |
| P3 | **Сервисы на Windows** (фоновая работа) | UI-сессия Windows ≠ системный сервис | поднять локального воркера как **Windows Service** через NSSM **или** запускать в WSL2 с systemd |
| P4 | **ComfyUI/Forge API** на 8 GB VRAM | OOM на тяжёлых workflow | строгий список workflow «дёшево по VRAM», health-check перед запуском |

### 1.4. Эксплуатация и безопасность

| № | Риск | Последствие | Рекомендация |
|---|------|-------------|--------------|
| S1 | **Локальный ПК — рабочий компьютер семьи?** | случайные перезагрузки, игры, конкуренция за GPU | отдельный пользователь Windows для воркера, ограничение по приоритетам/GPU-памяти |
| S2 | **Логирование PII при рендере** (имена и тексты подписчиков, сообщения) | хранится локально | минимизация: воркер получает только обезличенный job-описатель и ассеты |
| S3 | **Бэкап локальных моделей и пайплайнов** | при отказе диска — потеря 50–100 ГБ | хеши моделей и манифест в Git; повторяемая установка скриптом |
| S4 | **Лицензии моделей** (SD, FLUX и т.п.) | коммерческое использование требует лицензий | использовать модели с разрешённой коммерцией, фиксировать в README |

### 1.5. Аналитика и идемпотентность задач

| № | Риск | Последствие | Рекомендация |
|---|------|-------------|--------------|
| Q1 | **Дубли публикаций при перезапуске воркера** | один и тот же ролик уходит в YT/VK дважды | очередь с `job_id` и `idempotency_key`, состояние «started→done→published» на VPS |
| Q2 | **Расхождение «job завершён», но файл не дошёл до VPS** | в БД статус «готов», в S3/VPS файла нет | двухфазное завершение: «artifact_uploaded» → «job_done» только после проверки чексуммой |

## 2. Универсальные требования (наследие v10/v11/v12 + расширения для гибрида)

К ранее принятым добавляются:

1. **Очередь задач — на VPS, исполнение — на ПК.** ПК **никогда** не источник правды, только воркер.
2. **Контракт `RenderJob`:** JSON с `job_id`, `type` (`video.cut`, `video.hardsub`, `image.gen`, `transcribe`), `inputs[]` (URL/чексумма), `params`, `output_spec`. ПК скачивает входы, складывает выход в S3 / на VPS по WireGuard.
3. **Идемпотентность** через `idempotency_key = sha256(inputs+params)`.
4. **Отчёт о ресурсах:** ПК-воркер сообщает в `/heartbeat` GPU temp, VRAM used, disk free, version. Дашборд показывает.
5. **Расписание окон:** GPU-задачи — в окне 02:00–06:00 МСК (как в v11) или по запросу через дашборд; вне окон — только лёгкие inference.
6. **Версионирование артефактов:** каждое видео имеет manifest (исходники, srt, cuts.json, output) для повторяемости.
7. **Аварийный «PC offline»:** очередь продолжает копиться, дашборд алёртит, публикация автоматически НЕ деградирует на платный API без явного approve.

## 3. ВАРИАНТЫ РЕАЛИЗАЦИИ

Учитывая, что заказчик уже предложил два сценария (Гибрид VPS+ПК и Соло-локалка), формируем **три** строго оцениваемых варианта:

- **A. Гибрид VPS + ПК** — рекомендуемый, привязан к существующей инвентаризации (включая ПК).
- **A′. Соло-локалка** — упрощённый вариант пользователя «Б»: всё на одном ПК.
- **B. Чистый лист** — без привязки к ПК и VPS, целевая «зрелая» архитектура.

---

### 3.A. ВАРИАНТ A — «Гибрид VPS + Локальный ПК» *(рекомендуется)*

**Принцип:** VPS — это «нервная система» (онлайн 24/7, лёгкие задачи). ПК — это «мышцы» (GPU on-demand). Никакая критичная функция не зависит от того, включён ли ПК прямо сейчас.

#### 3.A.1. Состав

- **На VPS** (как в v12.A) — `empire_main`, `empire_dashboard`, `empire_webapp`, `empire_gdepar`, `empire_worker`, `empire_sales`, `empire_metrics`, `empire_video_dispatcher` (новый: ставит задачи в очередь, не рендерит сам).
- **На ПК** — `empire_gpu_worker`:
  - на **WSL2 Ubuntu 22.04** (рекомендуется) или нативно на Windows как сервис (NSSM);
  - забирает `RenderJob` из очереди VPS через WireGuard;
  - выполняет (`ffmpeg -c:v h264_nvenc`, `faster-whisper`, `comfyui-api`);
  - кладёт артефакты в S3 (Selectel/Yandex/Backblaze) **или** в VPS по `rsync over WG`;
  - шлёт `done` с `output_uri` и `sha256`.
- **Хранилище артефактов:** S3 (приоритет) — экономит интернет дома и трафик VPS.
- **Аутентификация ПК-воркера:** mTLS поверх WG, либо токен с коротким TTL.

#### 3.A.2. Поток `RenderJob`

1. Редактор в дашборде нажимает «Собрать Shorts из ролика URL» → `job_id` создаётся в `video_jobs` (на VPS).
2. `empire_gpu_worker` опрашивает (или получает push) очередь, забирает job.
3. Шаги ПК:
   - `yt-dlp` → `raw/<job_id>.mp4`;
   - `whisper` (faster-whisper medium int8) → `srt`;
   - LLM (на OpenRouter) → `cuts.json` (тайминги нарезок);
   - `ffmpeg -c:v h264_nvenc` → нарезка + хардсаб → `out/<job_id>_<n>.mp4`;
   - выгрузка в S3 + статус «artifact_uploaded» по чексумме.
4. VPS адаптеры публикации (TG/VK/YT/Дзен) забирают артефакт из S3 и публикуют.

#### 3.A.3. Сеть и безопасность

- WG: ПК — клиент, VPS — сервер. Reconnect автоматически, ключи защищены.
- S3 — отдельный bucket для артефактов, lifecycle rule «удалить через N дней».
- Очередь — Redis на VPS (легко) или таблица `video_jobs` в Postgres/SQLite (если без Redis).
- Лог heartbeat ПК (GPU temp/VRAM/диск) — каждые 30 c в `analytics.db` / `pc_status`.

#### 3.A.4. Расписание и нагрузка

- День: только лёгкие GPU-задачи (embeddings, мелкая транскрибация).
- Ночь (02:00–06:00): тяжёлые рендеры. ПК может **спать днём**, просыпаться по Wake-On-LAN, либо включаться по расписанию.
- Лимиты VRAM/CPU на воркере через `--gpu-memory-fraction` и приоритеты процессов.

#### 3.A.5. Фазы (вариант A)

| Фаза | Содержание | Критерий приёмки |
|------|------------|------------------|
| A.0 | **Освободить ≥150 GB на ПК**, поставить NVMe под `D:\models` | свободно ≥100 GB на диске моделей |
| A.1 | WSL2 + CUDA toolkit + драйверы + ffmpeg/NVENC + `faster-whisper` | `nvidia-smi`, `ffmpeg -hwaccels` показывают cuda/nvenc |
| A.2 | WireGuard ПК↔VPS, heartbeat в дашборде | в дашборде статус «PC online», задержка <100 ms |
| A.3 | Очередь `video_jobs`, контракт `RenderJob`, прогон тестового job | первый ролик с NVENC + хардсаб, артефакт в S3 |
| A.4 | Полный пайплайн yt-dlp→cuts→hardsub→publish | первый авто-цикл за ночь |
| A.5 | Опционально: ComfyUI/SD Forge API для обложек | замена 50% обложек на локальные |
| A.6 | (как v12.A.7) AI Insights + эксперименты с учётом GPU-метрик | первый отчёт |
| A.7 | (как v11.A.5) Коммерческое ядро | без изменений |

#### 3.A.6. Когда апгрейдить ПК

- Постоянный OOM на VRAM → 4070/4080 (16 GB) или 4090 (24 GB).
- DDR3/i7-3770 «упирается» на этапе декодинга 4K → платформа DDR5 (i5-12400/13400 — недорогой апгрейд).
- Стабильно ≥6 ч рендера/сутки → колокейшен ПК в дата-центре или переход на вариант B.

### 3.A′. ВАРИАНТ A′ — «Соло-локалка» (пользовательский «вариант Б»)

**Принцип:** Отказываемся от VPS, всё на ПК + Cloudflare Tunnel/Ngrok для публичного доступа.

#### Плюсы

- 0 ₽ за VPS.
- Все большие файлы локально — нет передач по сети.

#### Минусы (зафиксировать риски, прежде чем выбирать)

- **CF Tunnel** не предназначен для тяжёлого видеотрафика, есть ToS-ограничения.
- **Стабильность 24/7** домашнего ПК + Win10/EOL ниже, чем у VPS.
- **Падение интернета/электричества** = всё умерло, включая платежи и боты.
- **Боты TG/MAX/VK** часто плохо переносят разрывы long-polling.
- Сложнее **SSL/домены/почта** для коммерческих сайтов.
- **Сложно отделить «контентную» нагрузку от семейного использования** ПК.

#### Где допустимо

- Только как **dev-окружение** или MVP без коммерческих платежей и без обещаний SLA.

---

### 3.B. ВАРИАНТ B — «Чистый лист» (без привязки к ПК и VPS)

К B из v11/v12 добавляется конкретика по GPU:

- **GPU on-demand:** RunPod / Vast.ai / Selectel GPU Cloud — поднимаются под job и гасятся.
- **Контейнеры рендера:** `Dockerfile` с `nvidia/cuda` + `faster-whisper` + `ffmpeg-nvenc` + `comfyui` — повторяемая среда.
- **Cold start:** ~30–90 c, обходится pre-warm пулом 1 машины ночью.
- **Стоимость:** RTX 4060-эквивалент ~25–60 ₽/ч (в РФ), при 4 ч/сутки = ~3–7 тыс ₽/мес, что близко к домашнему электричеству + амортизации.
- Плюс: можно мгновенно масштабироваться (несколько GPU параллельно) под пик.
- Минус: оплата по кредитной карте (для зарубежных провайдеров) — операционно неудобно.

Это целевая архитектура, когда:
- ПК упирается в VRAM/диск;
- появляется команда, и нужно изолировать окружения;
- бизнес начинает зависеть от SLA рендера.

## 4. Сравнение вариантов

| Аспект | A. Гибрид VPS+ПК | A′. Соло-локалка | B. Чистый лист |
|--------|------------------|------------------|----------------|
| 24/7 онлайн (боты, сайты) | да (VPS) | хрупко | да |
| Стоимость инфры/мес | ~1 000 ₽ + S3 + ~электричество ПК | электричество, 0 ₽ за VPS | 3–10 тыс ₽ (GPU on-demand) |
| GPU доступен | по расписанию/требованию | всегда | по требованию |
| Сложность инфры | средняя | низкая | высокая |
| Риск SPoF | низкий (две точки) | высокий | низкий |
| Подходит для платежей/SLA | да | **нет** | да |
| Time-to-market | 3–6 недель | 1–2 недели | 6–10 недель |
| Управляемость семьёй | важно (ПК дома) | критично | не важно |
| Подходит как стартовая | **да** | dev/MVP | при бюджете |

**Рекомендация:**

1. Сделать **A.0 (освободить диски) → A.3 (WG + контракт RenderJob)** — это блокирующее.
2. Идти по варианту **A (Гибрид)** до выхода в стабильную монетизацию.
3. Опцию **A′ (Соло)** использовать только для проб (например, для рендера-MVP на выходных), **не** как production.
4. План **B** держать на этапе перехода через ~1 000 платящих или ≥6 ч рендера/сутки.

## 6. Критерии успеха v13

1. **Готовность ПК-воркера:** свободно ≥100 GB, `nvidia-smi`, `ffmpeg -hwaccels` показывают NVENC, `faster-whisper` рендерит тест за <2× длительности аудио.
2. **Стабильный WG-туннель:** uptime ≥99% в окне 02:00–06:00 за 14 дней.
3. **Видеоконвейер:** ≥3 Shorts/сутки автоматически за ночь, дубли публикаций = 0.
4. **Производительность:** транскрибация 60 мин подкаста ≤ 30 мин (на small/medium int8) или ≤ 90 мин (large на 8 GB VRAM с оффлоадом).
5. **Деградация под выкл. ПК:** боты, сайты, дашборд, продажи — продолжают работать; в дашборде статус «PC offline»; очередь рендера ждёт.
6. **Безопасность:** артефакты в S3 с lifecycle TTL; на ПК нет PII пользователей; модели и зависимости пин-версии.

## 7. Практические советы

- **Не делайте ПК «единственной точкой».** Самое ценное (продажи, контент) держите на VPS.
- **S3 = ваш буфер.** Передача через WG напрямую — только когда S3 нет. Дома upload медленнее, чем у VPS.
- **WSL2 > нативный Windows** для рабочей нагрузки: один тулчейн с Linux-серверами, проще скрипты и зависимости.
- **Модели маленькие, артефакты — большие.** Шортсы H.264 NVENC ~ 8–15 МБ на 60 c — это нормально. SDXL-картинка 1024×1024 ~ 1–3 МБ.
- **Никогда не публикуйте напрямую с ПК.** Только через VPS-адаптеры, для идемпотентности и логов.
- **Wake-on-LAN + расписание** — ПК спит днём, просыпается ночью; экономия электричества ~50%.
- **Сначала NVENC и `faster-whisper`. ComfyUI/SD — потом**, когда первый цикл уже стабилен.
- **Для рендера используйте `--gpu-memory-fraction`** или утилиту `nvidia-smi --gpu-reset` в скриптах при VRAM-фрагментации.
